## 一、 需求搜集背景与业务痛点调研

### 1. 调研背景
在校园图书分馆、企事业单位阅览室及社区图书角的日常管理中，由于缺乏专业的大型集成管理系统（ILMS）以及高昂的采购与运维成本，大量中小型图书室仍依赖传统的手工纸质登记或基础 Excel 表格记录借还。这种传统方式在读者借阅规模扩张时暴露出了严重的效率与管理瓶颈。

### 2. 传统图书借还核心痛点
1. **人工记账效率低下且易错**：登记借还全靠手工手写或人工录入表格，易出现借书证号、ISBN、图书书名录错问题。
2. **在架库存无法实时核验**：借出与归还信息不同步，经常出现“读者赶到借阅室却发现图书早已被借出”或“系统记录有书但书架无书”的脱节现象。
3. **借阅超期追踪与罚金核算繁重**：人工很难每日逐条比对应还日期，无法及时对逾期读者进行预警或催还，容易造成馆藏资产流失。
4. **统计分析缺乏数据支撑**：无法自动生成借阅量趋势图、读者借阅偏好、热门图书排行等数据，图书采购与馆藏调配缺乏科学依据。
5. **传统软件庞大臃肿且部署门槛高**：市面上成熟的商业图书软件往往依赖重量级关系型数据库与复杂集群中间件，在 1 核 1G 或 2 核 1G 的轻量级边缘服务器或云主机上难以平稳运行。

## 二、 用户角色与用户故事 (User Stories)

本项目设计并实现了严谨的基于角色的访问控制（RBAC），涵盖三类核心用户：

### 1. 读者 (Reader) - 借阅终端用户
- **US-01 注册与自主认证**：作为一名读者，我希望能够自主注册账号并绑定个人借书卡号，以便快速登录系统使用借阅服务。
- **US-02 图书检索与分类筛选**：作为一名读者，我希望能通过关键词（书名、作者、ISBN）或分类目录快速检索图书，并直观查看每本书的在架剩余数量，避免跑空。
- **US-03 在线借阅与一键发起**：作为一名读者，我希望能在选定图书后在线直接发起借阅申请，由系统自动扣减在架库存并生成借阅单据。
- **US-04 个人借阅跟踪与到期提醒**：作为一名读者，我希望随时查看自己“在借中”、“已归还”、“已逾期”的单据，清晰掌握应还日期与剩余借阅天数。
- **US-05 在线自主续借**：作为一名读者，如果我尚未读完且图书未逾期，我希望在规定允许次数内一键续借延期 30 天，无需专程前往人工柜台。

### 2. 图书管理员 (Librarian) - 馆藏与借还运营人员
- **US-06 新书采编入库**：作为一名图书管理员，我希望能录入新进图书的 ISBN、书名、作者、出版社、分类、物理架位及总册数，系统自动生成在架库存。
- **US-07 书目维护与上下架**：作为一名图书管理员，我希望能随时修改图书信息、补充复本库存；当图书报废时，若当前在借数为 0，允许执行注销下架。
- **US-08 柜台借还与核验代还**：作为一名图书管理员，我希望能根据借阅流水快速办理读者还书验收，系统自动回补图书在架库存并记录实际归还时间。
- **US-09 逾期图书催还与状态监控**：作为一名图书管理员，我希望能一键筛选所有超期未还的单据，查看借阅人联系方式并进行催还。

### 3. 系统管理员 (Admin) - 系统运维与全局管理主管
- **US-10 用户全生命周期管理**：作为一名系统管理员，我希望能查看全站用户列表，调整用户角色（提升管理员/撤销），以及对违规违约账号进行冻结或解封。
- **US-11 运营看板与可视化洞察**：作为一名系统管理员，我希望通过大屏看板直观监控全馆图书总数、在借册数、读者总数、近 7 天借还趋势以及分类占比，为馆务决策提供支撑。
- **US-12 容器化一键部署与极速启动**：作为系统运维负责人，我希望项目支持标准 Docker 容器化打包，在 2 核 1G 低配云服务器上无缝一键启动运行，内存占用低且稳定可靠。

## 三、 功能性需求清单 (Functional Requirements - MoSCoW 模型)

按照行业标准的 **MoSCoW (Must-have / Should-have / Could-have / Won't-have)** 模型对系统需求进行分级界定：

| 需求编号 | 需求模块 | 需求描述 | 优先级 | 交付状态 |
| :--- | :--- | :--- | :--- | :--- |
| **FR-01** | 用户认证 | 支持用户名/密码登录，采用 Passlib (bcrypt) 加盐哈希，签发标准 JWT Token | **Must (必须)** | 100% 已实现 |
| **FR-02** | 用户认证 | 支持读者自主注册，自动分配 reader 角色与全局唯一借书卡号 | **Must (必须)** | 100% 已实现 |
| **FR-03** | 权限控制 | 基于 RBAC 的动态路由控制与后端接口依赖注入鉴权（admin / librarian / reader） | **Must (必须)** | 100% 已实现 |
| **FR-04** | 图书分类 | 树形/列表分类维护，支持新增分类、编辑名称及唯一代号校验 | **Must (必须)** | 100% 已实现 |
| **FR-05** | 图书检索 | 支持书名、作者、ISBN 模糊多条件组合检索与分页加载 | **Must (必须)** | 100% 已实现 |
| **FR-06** | 图书管理 | 图书采编入库、书架物理位置（如 3F-A-02）标记、总册数与可借册数初始化 | **Must (必须)** | 100% 已实现 |
| **FR-07** | 图书管理 | 图书信息修改、复本增补入库、安全下架校验（借出未还时禁止下架） | **Must (必须)** | 100% 已实现 |
| **FR-08** | 核心借阅 | 读者在线借阅图书，数据库事务内原子校验库存并扣减 `available_copies` | **Must (必须)** | 100% 已实现 |
| **FR-09** | 借阅风控 | 借阅前置校验：单人最多限借 5 本、存在逾期图书时熔断阻断借阅 | **Must (必须)** | 100% 已实现 |
| **FR-10** | 核心归还 | 图书归还处理，原子释放库存回补 `available_copies`，更新单据状态为 RETURNED | **Must (必须)** | 100% 已实现 |
| **FR-11** | 在线续借 | 读者在线续借，限制每单仅可续借 1 次，自动在原应还时间上顺延 30 天 | **Must (必须)** | 100% 已实现 |
| **FR-12** | 借阅监控 | 借阅记录列表分页筛选，支持按状态（BORROWED/RETURNED/OVERDUE）过滤 | **Should (应该)** | 100% 已实现 |
| **FR-13** | 数据大屏 | 统计总览卡片：藏书种类、总册数、在借册数、读者数、借还人次统计 | **Should (应该)** | 100% 已实现 |
| **FR-14** | 数据图表 | 近 7 天借还趋势折线图、图书分类占比环形图、热门借阅 Top 10 | **Should (应该)** | 100% 已实现 |
| **FR-15** | 用户管理 | 管理员查看用户列表、重置密码、修改角色、启用/停用账户状态 | **Should (应该)** | 100% 已实现 |
| **FR-16** | 自动状态 | 借阅记录自动根据当前系统时间判定并标记是否超期 | **Could (可以)** | 100% 已实现 |
| **FR-17** | 逾期罚金 | 逾期天数计算与虚拟计费规则（0.5元/天），留有支付接口扩展字段 | **Could (可以)** | 100% 已实现 |

## 四、 非功能性需求清单 (Non-Functional Requirements)

| 指标维度 | 具体需求指标 | 技术对策与保障机制 | 达成结论 |
| :--- | :--- | :--- | :--- |
| **接口响应性能** | 系统常规 CRUD 接口响应时间 $\le 200\text{ms}$，大屏统计聚合 $\le 500\text{ms}$ | 后端采用异步框架 FastAPI，SQLAlchemy 字段索引与只读轻量聚合 | 实测响应 $< 50\text{ms}$，达标 |
| **弱硬件资源适应性** | 满足在 2 核 CPU、1GB 内存的低配云服务器上无卡顿构建与长期稳定运行 | 前端采用现代化原生 SVG 轻量图表引擎取代重型 ECharts；精简依赖包；Nginx 反代静态资源 | 内存占用仅 $\approx 180\text{MB}$，完美达标 |
| **数据一致性 (ACID)** | 借还过程中严禁出现“库存为负数”、“虚假借出”或“借出但库存未减”等数据不一致 | 采用数据库显式事务管控与原子条件更新语句，利用 SQLite WAL 预写日志保障并发读写安全 | 自动化测试验证 100% 达标 |
| **系统安全性** | 用户密码严禁明文传输与存储；规避常见 OWASP Top 10 漏洞（SQL 注入、XSS、CSRF） | 后端采用 Passlib + bcrypt 加盐哈希算法；ORM 参数化查询防 SQL 注入；Pydantic 强类型严格校验；JWT 安全校验 | 经代码安全审查通过 |
| **系统可移植性** | 消除“在我的电脑上能跑，在服务器上跑不起来”的环境依赖问题 | 全栈采用 Docker 容器化打包；编写一键部署 `docker-compose.yml` 与环境配置文件 | 阿里云 ECS 生产环境验证通过 |
| **前端打包效率** | 前端 Vite 生产环境构建时长控制在 10 秒以内，杜绝因内存爆满导致系统死锁 | 优化依赖结构与 CSS/JS 分块打包，本地构建时长降至 2.4 秒 | 彻底解决构建卡死问题 |
