## 一、 审查背景与范围

LibraryHub 系统旨在为中小型图书室打造一套轻量、高可靠的现代化图书借阅管理平台。为保证系统的工程规范性、运行稳定性与投产安全性，在系统完成编码与生产部署后，开展了全方位的工程综合审查。

本次审查覆盖以下四大核心维度：
1. **系统技术架构与数据模型合理性**：考察前后端解耦程度、E-R 关系设计、事务原子性控制及高并发读写策略。
2. **代码质量与工程规范性**：审查后端 Python 代码结构（PEP8 规范、Pydantic 校验、异常处理）与前端 Vue 3 工程规范（组合式 API、Pinia 状态管理、按需加载）。
3. **低资源环境性能攻坚与优化审查**：重点复盘在 2 核 1G 内存云服务器上前端构建卡死、Alpine musl 线程死锁的排查与优化对策。
4. **安全合规与鉴权防护**：审查密码存储安全、JWT Token 签名、SQL 注入防御、越权访问隔离及 Nginx 静态文件分发安全性。

## 二、 架构与数据库设计审查结论

### 1. 架构解耦与选型评价
- **前后端完全分离**：前端为纯静态 Vue 3 SPA 应用，后端为纯无状态 RESTful API 服务，网络边界清晰，职责明确。
- **持久化设计**：采用 SQLite 3 配合 `PRAGMA journal_mode=WAL`（预写式日志模式），实现了极简轻量化的单文件存储，避免了 MySQL/PostgreSQL 额外占用数百兆内存的问题；同时通过 Docker Volume 挂载 `/app/data`，彻底保障了容器更迭时不丢失业务数据。
- **事务与并发防超卖**：在处理核心“借书”与“还书”逻辑时，代码中显式采用了数据库事务（`db.commit()` / `db.rollback()`），并结合行级条件更新（`available_copies > 0`），从根源杜绝高并发超借超卖，设计严谨合理。

### 2. 数据模型设计评价
- **用户模型 (`users`)**：密码字段定义为 `hashed_password`，无任何明文泄露风险；预留了 `card_number`（借书卡号）唯一索引，符合高校与企事业单位借阅证管理惯例。
- **图书模型 (`books`)**：建立了 `isbn` 唯一约束与索引，设计了 `location`（物理架位）与 `available_copies`（在架余量），满足真实图书采编流通需要。
- **借阅单据模型 (`borrow_records`)**：外键关联清晰，建立了 `user_id`、`book_id`、`status` 及 `due_date` 的单列与联合索引，确保多维度报表查询响应迅速。

## 三、 代码质量与工程规范审查

### 1. 后端代码质量 (Python / FastAPI)
- **类型安全**：全面引入 Pydantic v2 进行请求与响应体的强类型模式声明（Schema），在输入层彻底阻断脏数据与注入风险。
- **权限依赖注入**：利用 FastAPI 的 `Depends` 机制，编写了可复用的 `get_current_active_user`、`require_admin` 等安全依赖，业务代码中无需重复编写权限判断逻辑，遵循了 DRY（Don't Repeat Yourself）原则。
- **自动化测试完备**：编写了涵盖所有关键业务用例的 Pytest 自动化测试集（`tests/test_api.py`），利用独立内存数据库运行，7/7 用例 100% 跑通，无破坏性修改遗留。

### 2. 前端代码质量 (Vue 3 / Vite)
- **现代化语法**：全面遵循 Vue 3 `<script setup>` 组合式 API 规范，组件逻辑内聚高，可读性好。
- **状态与路由管理**：使用 Pinia 进行用户 Token 与当前资料的全局状态持久化；配置了 Vue Router 全局路由前置守卫（`beforeEach`），读者与管理员路由严格分流。
- **网络通信封装**：统一封装 Axios 实例，提供全局拦截器（自动附加 JWT Bearer Token、统一捕获 401 自动跳转登录页）。

## 四、 核心性能攻坚复盘审查 (1G 内存云主机构建卡死问题解决)

在审查过程中，评审团队重点复核了开发者在低配云服务器上遇到的“前端构建卡死”问题的技术攻坚过程：

### 1. 问题复盘
- **运行环境**：2 核 CPU、1GB 内存、30GB 存储的阿里云轻量 ECS。
- **故障现象**：在云主机上执行 `docker build` 时，前端 Vite 构建进度长时间卡死在 `transforming... 1684 modules` 阶段，最终导致 SSH 连接中断或宿主机 OOM。
- **深层原因剖析**：
  1. 引入了完整的 ECharts 5 及其重量级依赖，其内部庞大的 Canvas/WebGL 算法库在打包阶段消耗瞬时内存峰值超过 1.2GB，远超服务器物理可用内存上限。
  2. 原前端 Dockerfile 采用 `node:20-alpine` 镜像作为构建阶段基底，由于 Alpine Linux 的 `musl libc` 在极度受限的多线程高并发内存申请场景下存在互斥锁（mutex）死锁竞争缺陷，导致 CPU 占用归零而进程永久挂死。

### 2. 优化方案与落地成效
- **对策一：自主研发原生响应式 SVG 图表组件**  
  开发者彻底剥离了重型 ECharts 依赖，利用 Vue 3 的动态数据绑定与响应式计算属性，手写了极轻量的原生 SVG 折线趋势图（带数据点悬停提示）与环形分布图。不仅完全消除了打包内存负担，而且组件渲染丝滑流畅。
- **对策二：调整构建策略与 Nginx 交付模式**  
  采用“宿主机/开发机高速预编译 + Alpine Nginx 极轻镜像直接装载”方案。本地构建时间仅需 **2.4 秒**，Docker 镜像体积大幅缩减至 23MB，启动运行仅需几毫秒。
- **对策三：修正 Nginx 生产 MIME 配置**  
  修复了 Alpine Nginx 默认未引入 MIME 文件导致浏览器以 `text/plain` 拦截 ES Module 的问题，加入了 `include /etc/nginx/mime.types;`，确保前端页面在公网零白屏秒开。

**审查结论**：该性能攻坚展现了开发者出色的底层原理分析能力与敏捷解决复杂工程问题的能力。
