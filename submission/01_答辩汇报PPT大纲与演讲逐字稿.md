### 第 3 页：项目背景与痛点分析 (Background & Pain Points)

* **现实痛点**：
  - 传统校园与社区图书馆借还登记依赖人工，并发效率低，极易产生错账漏账；
  - 纸质借书证容易丢失伪造，在借册数核对繁琐，借期逾期缺乏自动化熔断与滞纳金结算机制；
  - 现存许多管理系统过于庞大臃肿，对服务器内存硬件要求苛刻，小型图书馆无力承担高额运维成本。
* **系统核心解决目标**：
  - **轻量化微服务**：内存开销控制在 200MB 以内，在 1G 内存小服务器上秒级启动、顺畅运行；
  - **严密业务闭环**：借书、续借、超期滞纳金计算、还书回补、催还熔断全流程自动化状态机流转；
  - **开箱即用**：支持 Docker 一键容器化克隆，一分钟快速复制部署上线。

> 🗣️ **【答辩演讲逐字稿 - 01:15 ~ 02:00】**  
> “在项目构思初期，我调研了高校自习室与中小型图书室的实际运营现状。市面上现有开源系统大多基于笨重的老旧架构，不仅内存动辄吞噬数个 G，且借还并发时极易发生超借超卖。为此，我立足于‘极致轻量’与‘高可靠事务’两大原则，启动了 LibraryHub 的研发。”

### 第 4 页：系统总体架构与技术栈选型 (Architecture & Tech Stack)

* **架构分层设计 (Clean Architecture)**：
  - **接入层**：Nginx 反向代理网关，动静分离，统一暴露标准 HTTP 80 端口，开启 Gzip 压缩与静态缓存；
  - **表现层**：Vue 3 组合式 API + Vite 5 + Element Plus + Pinia + Vue Router 4，纯响应式单页 SPA；
  - **应用业务层**：Python FastAPI + Uvicorn 异步高并发驱动，Pydantic v2 强类型参数清洗，JWT Bearer 鉴权；
  - **持久化层**：SQLAlchemy 2.0 ORM + SQLite 3 (WAL 预写日志并发模式)，Docker Named Volume 持久化存储。

> 🗣️ **【答辩演讲逐字稿 - 02:00 ~ 02:45】**  
> “在技术架构选型上，我没有盲目跟风引入复杂臃肿的微服务全家桶，而是选用了最契合轻量高性能的 Python FastAPI 与 Vue 3。FastAPI 基于 Starlette 与 Pydantic，单机吞吐量比传统框架高出数倍，自带交互式 OpenAPI 文档；前端采用现代化的 Vite 构建；数据存储采用开启 WAL 模式的 SQLite3，结合 Docker 宿主机持久化卷挂载，既做到了零外部依赖免运维，又杜绝了容器重启数据丢失。”

### 第 5 页：核心业务流转与并发防超借设计 (Core Business & Concurrency Control)

* **借还流转状态机**：
  - 图书在架（可借） $\rightarrow$ 资格校验（在借本数上限校验、逾期未结清熔断拦截） $\rightarrow$ 原子扣减库存 $\rightarrow$ 生成流水（`BORROWED`） $\rightarrow$ 在线续借（限1次/延期30天） $\rightarrow$ 逾期天数与滞纳金核算（每日0.5元） $\rightarrow$ 归还结清（`RETURNED`）并原子回补库存。
* **高并发防超借机制**：
  - 在数据库更新操作中引入条件原子操作：  
    `UPDATE books SET available_copies = available_copies - 1 WHERE id = :id AND available_copies > 0;`
  - 彻底规避传统“先查后改”在多读者同时借走最后一本书时产生的超卖负库存并发风险。

> 🗣️ **【答辩演讲逐字稿 - 02:45 ~ 03:30】**  
> “图书管理系统最核心的技术难点在于并发事务。比如馆内某畅销书在架仅剩最后一本，多名读者在同一秒内发起借阅请求。如果采用先 SELECT 查询再 UPDATE 的传统写法，必将导致库存变成负数。在本项目中，我在持久层与服务层设计了严格的带条件原子写锁与事务回滚，确保无论高并发流量如何冲击，物理在架量与借阅单据绝对强一致。”

### 第 7 页：低配服务器（2核1G）性能调优深度复盘 (Performance Tuning Case)

* **面临挑战**：云服务器仅有 2核CPU / 1GB 内存，容器内运行 Vite 编译打包时因进程管道与 Alpine 线程缺陷发生假死卡顿。
* **攻关历程与解决之道**：
  1. **开启 Swap 虚拟内存**：配置 2GB 交换空间，防范峰值内存溢出；
  2. **剥离沉重依赖**：砍掉数十兆的庞大 ECharts 库，替换为高性能轻量原生 SVG，编译模块数由 2500+ 骤降至 1600+；
  3. **图标按需注册**：重构全局遍历注册逻辑，改为精准按需载入，内存开销削减 70%；
  4. **采用工业级 Nginx 生产镜像**：解耦开发期编译与生产期托管，生产镜像体积压缩到 20MB，运行内存仅 10MB，打包耗时从 5 分钟骤降到 **2.4 秒**。

> 🗣️ **【答辩演讲逐字稿 - 04:30 ~ 05:15】**  
> “在服务器部署过程中，我遇到了非常棘手的性能瓶颈：服务器只有 1GB 内存，初始构建时前端总是在打包阶段卡死。我没有妥协去升级昂贵的硬件，而是沉下心来进行性能分析，发现根本原因是全量 ECharts 和 Element 图标消耗了海量 AST 解析内存。我果断进行轻量化重构，用原生 SVG 替代重型图表库，并限制 Rollup 编译并发度。最终前端编译速度提升了近 100 倍，整个系统在 1G 内存服务器上运行如飞，展现了真正的工程优化实力。”

### 第 8 页：学习方法与解决问题思路 (Learning Methodology & Problem Solving)

* **自主探索与工程学习方法**：
  1. **现代 AI 结对编程 (AI Pair Programming)**：以架构师思维主导设计，借助现代 AI 助手快速排查容器底层系统日志与语法迁移（如 Pydantic v2 规范升级）；
  2. **从现象抓本质的排障思路**：
     - 白屏排查：不仅停留在前端代码，更通过 SSH 抓取 Nginx 日志发现缺少 `mime.types` 导致浏览器安全策略拦截；
     - 端口诊断：通过 `curl` 探测与端口扫描，精准诊断出外部公网被防火墙拦截，最终将端口收敛至免输入端口的标准 80 端口；
  3. **查阅官方一手文档**：阅读 FastAPI、SQLAlchemy 2.0 及 Vue 3 官方文档，杜绝网络陈旧过时的复制粘贴代码。
