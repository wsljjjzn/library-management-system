### Slide 3: 模块二 · 项目立项背景与中小型图书室传统痛点剖析
- **视觉版式**：三栏式卡片对比布局，每个痛点配有状态胶囊标签。
- **页面标题**：**项目立项背景与中小型图书室传统痛点剖析**
- **副标题说明**：传统人工手工记账与庞大商业软件的两极困境，催生了轻量高可用智能借阅系统的研发需求
- **卡片 1【痛点 1: 人工与 Excel 记账脱节 · 假库存严重】**：
  - *现象与危害*：很多中小学校园分馆、院系资料室仍依赖纸质借书本或人工表格录入。
  - *具体弊端*：登记繁琐，书名、ISBN、卡号极易发生笔误录错；借出与还入缺乏实时动态库存核验，经常出现“读者跑去书架发现早已借空”或“系统记录有书但书架无书”的脱节现象；馆藏盘点核对周期极长，资产流转效率极其低下。
- **卡片 2【痛点 2: 缺乏主动逾期风控机制 · 催缴成本高】**：
  - *现象与危害*：缺乏到期智能预警与主动权限限制，借还规则形同虚设。
  - *具体弊端*：管理员需每日手工翻查借据核对应还日期，催还滞后；市面很多模板大作业“仅在界面打个已逾期标签”，读者依然能随意借新书，无法实质性制约违约行为；长期超期未还与图书遗失屡禁不止，严重损害公共借阅权益。
- **卡片 3【痛点 3: 商业软件庞大臃肿 · 服务器成本高昂】**：
  - *现象与危害*：传统商业图书管理软件（ILMS）架构复杂，部署门槛极高。
  - *具体弊端*：动辄强依赖数 GB 内存的复杂数据库集群与中间件；基层单位通常仅有 1G 内存的轻量云服务器或边缘主机，商业软件根本无法启动运行；采购授权与每年云资源开销高达数万元，中小微图书馆无力承担。

### Slide 4: 模块二 · 系统总体开发思路与生产架构技术选型
- **视觉版式**：左侧展示四大开发原则，右侧呈现前后端分离生产技术栈矩阵。
- **页面标题**：**系统总体开发思路与生产架构技术选型**
- **副标题说明**：坚持前后端完全解耦、零冗余中间件、行级原子排他锁与自研轻量图表的极致高可用架构
- **左侧面板【整体开发设计四大核心准则】**：
  1. *极简轻量，算力友好*：坚持“零无用中间件”原则，剔除高内存消耗组件，全栈容器常驻内存压缩至 ~180MB，专为 2核1G 极限配置云服务器量身定制。
  2. *严密并发控制，数据强一致*：核心借还逻辑实行“数据库事务 + 行级条件排他锁”，杜绝负库存与超卖，保障每一本图书在架量物理与逻辑完全对应。
  3. *主动风控阻断，业务全闭环*：构建三道准入防火墙，名下有未结逾期图书立即自动熔断借阅权限；未逾期图书支持在线一键顺延 30 天续借。
  4. *云原生容器化，一键极速投产*：采用 Docker Compose 编排，支持宿主机数据卷持久化挂载，实现跨平台“零环境污染、单命令一键部署”。
- **右侧面板【全栈生产级技术选型矩阵】**：
  - 【前端框架】：Vue 3.4 (Composition API) + Vite 5.4 + Element Plus（响应式数据绑定，单组件内聚，打包仅 2.4 秒）；
  - 【后端框架】：Python 3.11 + FastAPI (ASGI 异步高性能，高并发读写下吞吐效率逼近 Go)；
  - 【数据校验】：Pydantic v2 (Rust 核心安全驱动，严格强类型入参校验，在输入层杜绝脏数据与 SQL 注入)；
  - 【数据存储】：SQLite 3.45 (PRAGMA journal_mode = WAL 模式，并发预写日志，读写互不阻塞，单文件快照，零额外常驻内存)；
  - 【安全鉴权】：Passlib (bcrypt 工业级加盐哈希) + PyJWT (HS256 签名无状态令牌)；
  - 【网关运维】：Nginx Alpine + Docker Compose v2 (数据卷持久化挂载)。

- **左侧卡片【生产环境遭遇的严重工程难题与根因排查】**：
