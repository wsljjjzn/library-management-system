### Slide 3: 项目背景与开发思路 (Background & Philosophy)
- **幻灯片标题**：行业痛点分析与开发设计思路
- **传统图书管理三大痛点**：
  1. *人工记账与 Excel 脱节*：书目借还无法实时同步，常常出现“系统有书、架上无书”的假库存；
  2. *借还风控缺失*：逾期全凭人工翻本核对，无法对长期超期读者进行主动权限熔断；
  3. *商业系统庞大臃肿*：动辄依赖数 GB 内存的大型中间件，在中小学校园微型阅览室、社区书屋的低配轻量服务器上难以部署运行。
- **整体开发设计思路**：
  - **极简轻量**：坚持“零多余中间件”原则，以极小资源开销释放极致性能；
  - **严密原子性**：借还事务强一致性，数据库行级条件锁杜绝负库存与超卖；
  - **智能风控**：多维度借阅限额、逾期自动熔断与单次顺延续借；
  - **一键交付**：容器化标准化编排，云端开箱即用。
- **视觉版式建议**：采用“痛点 VS 对策”对比双栏卡片，配合醒目的红绿状态图标。

> **【演讲逐字稿】（用时约 60 秒，累计 01:30 - 02:30）**  
> “接下来谈谈项目的立项背景与设计思路。我们在校园微型分馆和社区图书室调研时发现，很多中小型借阅室仍在使用纸质登记或基础 Excel，面临三大难题：第一是借还状态不同步，经常造成库存脱节；第二是读者逾期无法自动追踪和限制借阅权限；第三是市面上成熟的图书系统过于庞大，对服务器内存要求很高，而基层图书室往往只有 1G 内存的轻量云主机，根本跑不起来。  
> 针对这些痛点，我确立了 LibraryHub 的研发思路：坚持前后端完全解耦与极简架构设计，以高内聚的异步后端保障并发性能，以严密的数据库事务锁保障库存原子一致性，以智能风控实现主动熔断，同时通过前端轻量化重构，确保系统能在 1G 内存的极限低配服务器上流畅运行。”

### Slide 4: 系统总体架构与技术选型 (Architecture & Tech Stack)
- **幻灯片标题**：前后端分离生产架构与选型论证

  - 客户端浏览器 $\rightarrow$ Nginx 反向代理网关 (Port 80) $\rightarrow$ 静态资源缓存 / API 动态反代 $\rightarrow$ FastAPI 异步服务容器 (Port 8000) $\rightarrow$ SQLite WAL 模式数据库 (挂载宿主机持久卷)
- **技术栈深度论证**：
  - **后端**：Python 3.11 + FastAPI（基于 ASGI 事件循环，吞吐量逼近 Go/Node；Pydantic v2 基于 Rust 核心，强类型安全校验）；

### Slide 6: 【创新亮点 1】业务功能创新设计 (Functional Innovation - 满分 4 分)
- **幻灯片标题**：业务功能创新：智能风控、原子安全锁与卡号规范
- **创新点一：逾期阶梯风控与主动借阅权限熔断机制**
  - 区别于普通图书系统“仅标记逾期状态却不限制行为”的漏洞，本系统在读者发起借阅时强制触发三道准入防火墙：
    1. *未还额度校验*：单人最多借阅 5 本；
    2. *逾期熔断拦截*：名下只要存在 1 本未还逾期图书，系统自动熔断借阅权限，阻断新借请求；
    3. *单据状态自动判定*：借还接口自动比对服务器当前时间与应还时间，动态计算超期天数与违约金。
- **创新点二：库存行级原子锁与高并发防超卖**
  - 在底层借还逻辑中，采用显式事务结合原子条件更新：
    $$\text{UPDATE books SET available\_copies = available\_copies - 1 WHERE id = :id AND available\_copies > 0;}$$
    若影响行数为 0 立即抛出并发冲突并回滚事务，从根源杜绝多读者并发抢借导致的“负库存”。
- **创新点三：规范化条码借书卡号体系与防呆注销**
  - 用户注册自动颁发标准借书卡号（`CARD-YYYYMMDD-XXXX`）；图书下架时前置核验在借数，存在未还记录时强制阻断，守护馆藏资产。
- **视觉版式建议**：展示状态机流转图与准入拦截流程图，配合关键代码高亮。

> “接下来向各位老师重点汇报本项目的创新与优化模块。首先在业务功能设计上，实现了三大创新突破：

### Slide 7: 【创新亮点 2】技术方案与自研架构攻坚 (Technical Innovation - 满分 3 分)
- **幻灯片标题**：技术方案创新：自研原生轻量 SVG 引擎破解 1G 内存构建死锁
- **遭遇难题**：在 2 核 1G 内存的阿里云服务器上执行前端 Docker 打包时，进程持续卡死在 `transforming... 1684 modules`，导致 SSH 掉线与系统 OOM。
- **深层原理剖析**：
  1. *内存瓶颈*：引入的第三方大图表库（ECharts 5）包含庞大的 WebGL/Canvas 依赖，打包瞬间消耗内存超 1.2GB，瞬间挤爆云主机；
  2. *底层死锁缺陷*：Alpine Linux 的底层 `musl libc` 在多线程极度受限的内存竞争下存在互斥锁（mutex）死锁 Bug，导致 CPU 占用归零而进程永久挂死。
- **突破性解决方案**：
  - **创新一：自主研发纯原生响应式 SVG 矢量图表引擎**  
    彻底拔除重型外部图表库依赖，利用 Vue 3 的动态数据绑定与响应式计算属性，手写极轻量的原生 SVG 折线趋势图（带坐标网格与数据点悬停卡片）与环形分布图，零第三方依赖；
  - **创新二：构建与交付链路解耦重构**  
    采用开发机极速预构建 + Alpine Nginx 极轻镜像直接装载方案，生产镜像体积仅 23MB，构建时间从超时死锁大幅压缩至 **2.4 秒**，运行时内存节约 80%！
  - **创新三：现代 AI 辅助研发实战**  
    深度引入先进 AI 研发工具流辅助全栈重构、构建链路瓶颈智能定位与 Pytest 自动化测试用例全量生成（7/7 用例 100% 通过）。
- **视觉版式建议**：展示“优化前 VS 优化后”性能对比图表（构建耗时从 $\infty$ 降至 2.4s，内存从 1.2GB 降至 8MB）。

> **【演讲逐字稿】（用时约 80 秒，累计 05:50 - 07:10）**  
> “第二项创新是我们在技术方案与系统性能上的深度攻坚。  
> 在将项目部署到 1G 内存的阿里云服务器时，我遇到了一个极其棘手的工程难题：前端构建卡死。经过深入的系统级排查，我定位到了两大根因：一是引入的外部重量级图表库在编译时内存峰值突破 1.2G，远超机器承受能力；二是 Alpine Linux 的 musl 库在高并发内存受限场景下触发了互斥锁死锁竞争。  
> 面对这个问题，我没有选择简单加钱升级高配服务器，而是做了一次坚决的技术架构创新：我彻底剥离了重型外部依赖，利用 Vue 3 的响应式能力，自主研发了一套轻量级的原生响应式 SVG 矢量数据图表组件！  
> 这项创新不仅完美实现了折线图和环形图的动态交互，而且将前端构建时长彻底压缩到了 2.4 秒，全站容器运行时内存总计仅约 180MB，在 1G 内存机器上也能飞速运行。同时，在整个开发过程中，我深度运用了现代 AI 研发工具流来辅助代码重构和自动化测试编写，大幅提升了研发质量。”

### 问题 1：在高并发场景下，如何确保图书库存不会出现“超卖”（被借成负数）？
> **【标准应答逐字稿】**：  
> “谢谢老师的提问！这是借阅系统最核心的并发一致性问题。我在后端服务层采用了‘数据库行级条件原子更新 + 事务显式控制’双重防护机制：  
> 在执行借阅扣减时，不是简单在 Python 代码里读取库存判断后再保存，而是在同一事务内直接执行：  
> `UPDATE books SET available_copies = available_copies - 1 WHERE id = :id AND available_copies > 0;`  
> 借助数据库内部行锁的原子特性，只要该记录的可借库存已经为 0，该 SQL 影响的行数就会是 0。代码检测到影响行数为 0 时，立即回滚事务并向客户端抛出 400 库存不足业务异常。  
> 这样即便有数十名读者在同一毫秒内抢借同一本仅剩 1 册的热门图书，也只有拿到排他锁的第一条事务能够扣减成功，从底层物理上彻底杜绝了超卖和负库存的发生。”

---

### 问题 2：你们为什么选用轻量级 SQLite3 而不是更常见的 MySQL 或 PostgreSQL？它的并发读写性能如何保障？
> **【标准应答逐字稿】**：  
> “感谢老师的敏锐洞察！在技术选型之初，我深入权衡了业务场景与部署成本：  
> 传统 MySQL 进程启动常驻内存至少需要 300MB 到 500MB，对于我们面向的中小型校园阅览室或社区图书室而言，采购高规格服务器存在巨大的资源浪费。  
> 针对中小型图书室‘读多写少’（95% 以上请求为书目检索与状态查询，仅 5% 为借还写事务）的业务特征，我选用了轻量级嵌入式 SQLite3，并创新性地开启了 WAL（Write-Ahead Logging，预写式日志）模式。  
> 在 WAL 模式下，读操作和写操作互不阻塞，多个并发读者可以同时并发读取数据，而写操作在专用的预写日志中追加记录，不仅将系统常驻内存降低了 80% 以上，而且单机读吞吐每秒可轻松支撑数百次查询，同时配合 Docker 数据卷挂载保证了文件安全持久化，非常契合轻量高效的落地需求。”

---

### 问题 3：在 1G 内存服务器上前端构建卡死的问题，你是如何定位并彻底解决的？
> **【标准应答逐字稿】**：  
> “谢谢老师的提问！这个问题的排查是我实训中最有价值的技术攻坚之一。  
> 当时服务器在执行 `npm run build` 时频繁停滞在 module transform 阶段，内存消耗剧增导致 SSH 中断。我通过逐步排查定位到了两个深层原因：  
> 第一，第三方大图表库 ECharts 依赖的底层 Canvas/WebGL 算法库在 Rollup 分块编译时产生瞬时内存峰值超过 1.2G；  
> 第二，基础镜像 `node:20-alpine` 基于 musl libc，在极限内存争夺下存在多线程互斥锁（mutex）死锁 Bug，导致 CPU 归零挂死。  
> 解决思路上，我没有选择简单加钱升配置，而是选择自主重构：我彻底剥离了重型图表库，利用 Vue 3 的响应式数据绑定，自主手写研发了一套纯原生的响应式 SVG 折线图与环形图组件。  
> 重构后不仅完整保留了交互动效，而且打包时长从死锁超时缩减到了 2.4 秒，镜像体积缩减到 23MB，完美攻克了低配服务器的构建瓶颈。”

---

### 问题 4：读者身份认证采用 JWT，如何防止 Token 被盗用？用户点击“退出登录”后，旧 Token 怎么失效？
> **【标准应答逐字稿】**：  
> “感谢老师的提问！在系统安全性方面我采取了多层次的防护措施：  
> 首先，密码在数据库端经过工业级 `bcrypt` 加盐哈希加密存储，杜绝撞库；  
> 其次，签发 JWT 时采用强密钥 HS256 单向签名，并在 Payload 中注入了用户角色（RBAC 鉴权）与过期时间（exp），有效时长严格限制为 7 天，接口全面开启 CORS 跨域白名单校验；  
> 关于退出登录的 Token 失效问题：目前客户端通过清空 localStorage 中的 Token 切断后续请求；在生产高安全要求下，系统架构预留了‘服务端 Token 黑名单/版本号’扩展槽，在用户登出或管理员修改密码时递增用户的 `token_version`，这样即使截获旧 Token，调用接口时版本号不匹配也会被立即拒绝。”
